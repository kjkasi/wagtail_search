# Поиск по заголовкам страниц и документов — Design Specification

## Goal

Добавить в Bootstrap navbar динамический поиск по заголовкам опубликованных страниц и прикреплённых документов текущего Wagtail-сайта. Результаты должны появляться выпадающим списком во время ввода, без перезагрузки страницы.

## Confirmed decisions

- Поле поиска постоянно находится в navbar базового шаблона.
- Поиск запускается во время ввода после debounce-задержки около 250 мс.
- Backend endpoint: `GET /search/?q=<query>`.
- Endpoint возвращает JSON, а frontend строит выпадающий список.
- Для поиска используется Wagtail Search API, а не отдельный `title__icontains`-запрос.
- Ищутся все опубликованные страницы текущего сайта, включая страницы с `show_in_menus=False`.
- Корневая `HomePage` текущего сайта не показывается в результатах.
- Совпадение выполняется без учёта регистра по индексируемым заголовкам страниц.
- В выпадающем списке показывается не более 10 результатов.
- Запрос длиннее 200 символов отклоняется с ответом `400` и кодом ошибки `query_too_long`.
- Пустой или состоящий только из пробелов запрос не выполняет поиск.
- При отсутствии совпадений показывается сообщение `Ничего не найдено`.
- Каждый результат является ссылкой на соответствующую страницу или документ.
- Поиск по заголовкам прикреплённых документов добавляет типизированные результаты в тот же endpoint и dropdown, не меняя navbar-форму.

## Scope

### In scope

1. JSON view для поиска страниц и прикреплённых документов текущего Wagtail Site.
2. URL `/search/` в `config/urls.py`.
3. Поисковая форма в `home/templates/home/base.html`.
4. Dropdown результатов с пустым, загрузочным и безрезультатным состояниями.
5. Debounced AJAX-запросы из `frontend/main.js`.
6. Защита от устаревших ответов при быстром вводе нового запроса.
7. Базовая клавиатурная и screen-reader доступность dropdown.
8. Django-тесты endpoint и шаблонной интеграции.
9. Проверка сборки frontend assets.

### Out of scope

- Поиск по `ArticlePage.body`.
- Поиск по содержимому файлов документов.
- Отдельная страница полного списка результатов.
- Pagination или бесконечная прокрутка dropdown.
- Фильтры, категории и теги.
- Индексация новых пользовательских моделей.
- Изменение Wagtail admin.

## Architecture

### Backend

Добавить отдельный view `search(request)` в `home/views.py`. View принимает только GET-запросы и читает параметр `q`.

Алгоритм:

1. Обрезать начальные и конечные пробелы в `q`.
2. Для пустого запроса вернуть `JsonResponse({"results": []})`.
3. Найти текущий сайт через `Site.find_for_request(request)`.
4. Если сайт не найден, вернуть пустой список результатов.
5. Искать среди `Page.objects.live().descendant_of(site.root_page)`, исключив сам `site.root_page`, используя Wagtail Search API `.search(query)` и ограничив queryset первыми 10 результатами.
6. Если осталось место в лимите, искать документы через `Document.objects.search(query)`, ограничивая запрос оставшимся количеством результатов.
7. Возвращать только документы, на которые есть document-link в опубликованных `ArticlePage` текущего сайта; проверять только тела статей, потенциально содержащие найденные идентификаторы документов.
8. Сериализовать результаты как типизированные объекты `{ "type": "page"|"document", "title": ..., "url": ... }`.

Текущая модель `ArticlePage` не должна получать новый `search_fields` для `body`: на этом этапе поисковый индекс должен использовать заголовки страниц. Доступ к страницам определяется `live()`, а не `show_in_menus()`.

JSON-контракт:

```json
{
  "results": [
    {"type": "page", "title": "О компании", "url": "/about/"},
    {"type": "document", "title": "Руководство", "url": "/documents/guide.pdf"}
  ]
}
```

Для слишком длинного запроса используется статус `400` и контракт `{ "error": "query_too_long", "results": [] }`.

Для пустого запроса, отсутствующего текущего сайта и отсутствия совпадений используется тот же контракт с пустым массивом. Endpoint не должен выполнять поиск по POST и не должен возвращать draft-страницы.

### Template

В `home/templates/home/base.html` добавить форму с `role="search"`, полем с понятным `label`/`aria-label`, submit-кнопкой и контейнером dropdown. Форма использует `/search/` как action; JavaScript читает action формы, чтобы URL endpoint не дублировался в коде.

Контейнер результатов должен:

- находиться рядом с input внутри позиционируемого блока;
- быть скрыт, когда результатов нет;
- иметь `role="listbox"` и стабильный `id`;
- связываться с input через `aria-controls` и `aria-expanded`;
- содержать ссылки на найденные страницы и документы;
- показывать текстовое состояние `Ничего не найдено` без ссылки при пустом результате.

Форма должна работать внутри существующего responsive Bootstrap navbar и не ломать мобильный toggler.

### Frontend

В `frontend/main.js` сохранить текущие Bootstrap imports и добавить отдельный код поиска.

Поведение:

1. Найти форму и input по data-атрибутам/стабильным id; если их нет, не выполнять никакой логики.
2. На `input` запускать debounce около 250 мс.
3. До fetch скрывать список для пустого запроса; для непустого запроса показывать loading-state.
4. Запрашивать `GET` на action формы с URL-кодированным `q`.
5. Отменять предыдущий `AbortController` либо игнорировать ответ, если он относится к устаревшему запросу.
6. Отрисовывать title и url через DOM text/content APIs, а не небезопасной конкатенацией HTML.
7. Открывать dropdown при наличии результатов или сообщения; закрывать его при пустом запросе и при клике вне блока поиска.
8. По нажатию на результат переходить по обычной ссылке.
9. Поддержать Escape для закрытия списка и базовую навигацию Tab/стрелками без перехвата клавиш у других элементов navbar.

Сборка выполняется существующей командой `npm run build`; сгенерированные `static/site/main.css` и `static/site/main.js` не добавляются в Git, если это соответствует текущему `.gitignore`.

### Document search

Endpoint также ищет документы по заголовку через `Document.objects.search(query)`. В результаты попадают только документы, прикреплённые ссылками к опубликованным `ArticlePage` текущего сайта. Поиск по содержимому файлов остаётся за пределами этой версии. Текущая реализация не требует изменения HTML-формы или debounce-механизма для расширения типов результатов.

## Testing strategy

Django-тесты должны проверять:

1. `GET /search/?q=Visible` возвращает `200`, JSON и совпадающую страницу.
2. Поиск нечувствителен к регистру.
3. Пробелы вокруг запроса игнорируются.
4. В результаты попадают опубликованные страницы, даже если `show_in_menus=False`.
5. Draft-страницы и корневая `HomePage` не попадают в результаты.
6. Страница, в заголовке которой нет запроса, но в body которого он есть, не находится.
7. Пустой запрос и запрос без совпадений возвращают `{"results": []}`.
8. Запрос длиннее 200 символов получает `400` с кодом `query_too_long`.
9. Ответ ограничен 10 результатами, включая страницы и документы.
10. Базовый шаблон содержит поисковую форму, endpoint action, input и dropdown ARIA-атрибуты.
11. Существующие navbar, rich text и Bootstrap asset assertions продолжают проходить.

Frontend-проверка должна убедиться, что `npm run build` завершается успешно, а итоговый JavaScript содержит код поиска и Bootstrap bundle. Полноценные браузерные тесты autocomplete не требуются для первой версии; ручная проверка должна подтвердить открытие списка, переход по результату, Escape и работу внутри мобильного navbar.

## Acceptance criteria

- На любой публичной странице navbar содержит поле поиска.
- При вводе запроса через примерно 250 мс появляется dropdown максимум с 10 результатами: опубликованными страницами и прикреплёнными документами, совпадающими по заголовку.
- Скрытые из меню опубликованные страницы находятся; draft-страницы не находятся.
- Пустой запрос скрывает dropdown.
- При отсутствии результатов отображается `Ничего не найдено`.
- Клик по результату открывает соответствующую страницу или документ.
- Быстрый ввод не позволяет старому AJAX-ответу заменить результаты нового запроса.
- Поиск не выполняет полнотекстовый поиск по `ArticlePage.body`; body используется только для проверки ссылок на найденные документы, без отдельной страницы результатов.
- Существующий Bootstrap navbar toggler продолжает работать в desktop и mobile layout.
- Endpoint и frontend используют единый типизированный контракт для результатов страниц и документов.

## File layout

```text
config/urls.py                         # маршрут /search/
home/views.py                          # JSON search view
home/templates/home/base.html         # navbar form и dropdown container
home/tests/test_search.py              # endpoint и JSON contract tests
home/tests/test_pages.py               # template/navbar integration assertions
frontend/main.js                       # debounce, fetch и dropdown rendering
home/templates/home/search_results...  # не требуется: ответ JSON
```

## Risks and mitigations

- **Устаревшие AJAX-ответы:** использовать `AbortController` или request sequence token.
- **XSS через заголовки:** создавать текстовые узлы/назначать `textContent`; не вставлять серверные title через `innerHTML`.
- **Скрытые страницы:** фильтровать только `live()`, не использовать текущий `navigation_items`, который дополнительно применяет `in_menu()`.
- **Поиск по body по ошибке:** не добавлять `body` в `search_fields`; закрепить это endpoint-тестом. Тела статей читаются только для проверки ссылок на ограниченный набор найденных документов.
- **Отсутствующий Site:** возвращать валидный пустой JSON, а не 500.
- **Мобильный navbar:** сохранить Bootstrap markup и проверить сборку/существующие toggler assertions после добавления формы.
